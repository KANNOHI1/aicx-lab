テキスト入手前の全 Build（B8〜B11・C1・C2・D1・D2）が終わった後に、全教材・全問題へ**横断の敵対的レビューを1回だけ**入れる。HK 決定（2026-08-28、2026-08-29 に再確認）。

**3段階に分ける**

| 段 | 担当 | 見るもの |
|---|---|---|
| ① 機械検出 | node スクリプト | 長さ手がかり・型3順位語・ID重複・ケース字数・用語リンク漏れ。**モデルには出さない** |
| ② 本体レビュー | **Opus** | 事実誤り・正解の一意性・回跨ぎの矛盾・配分の穴・誤答肢の思想。判断が要るものだけ |
| ③ 見落とし探し | **Fable × effort:max** | ②の結果を渡し、completeness critic として「何が抜けているか」だけを問う |

**Why この配分か**
- 機械で潰せるものをモデルに出すのはトークンの無駄。②に集中させる
- B5 で Opus×28体が実欠陥4件を検出した実績があるので、本体は Opus で足りる見込み
- **「Fable でなければ検出できない」証拠は現時点で無い**。だから Fable は最後の見落とし探しに限定し、使用量を抑えつつ「Fable に価値があるか」を実測する。**③で何も出なければ、以後は Opus で足りると判断してよい**
- C1（模試エンジン）はコードなので別レンズ（動作検証：採点・タイマー・中断保存・localStorage）

**How to apply**
- **③に入る時点で「/model で Fable に切り替えてください」と HK にリマインドする。** Claude 側からモデルは変更できない
- 各 Build の安価な自己チェック（①相当）は最終レビューを待たず毎回やる。最終レビューだけにすると未検証 Build が積み上がる — 実例として第1〜7回に長さ手がかりが35件残り、2026-08-29 に一括是正する羽目になった

## 2026-08-31 追記：再オープン。F シリーズ完了後の横断レビューは「やる」

HK 指示「覚えておいて。諸々終わったらやろう」。

**なぜ必要か**: R0 の Opus 8体レビューは**再構築前のサイト**に対するもの。F0〜F11 で教材14回・問題234問・用語159語を全部作り直したが、**作り直した後の横断レビューは一度も回っていない**。通っているのは Build ごとの自己チェックと F10 の語彙総当たりだけ。

**実施タイミング**: サイト側の残作業（模試のケース比率是正・第1章の作問）が終わってから。順序を守る理由は、レビュー対象が動いている最中に回すと指摘が陳腐化するため。

## 2026-08-31 追記：R2 実施・完了。クローズ

G1（第1章の作問12問）完了後、HK が `/model` で Fable へ切替え「お願いします」と指示。**Fable サブエージェント8体**（章別6・ガイド回/横断整合1・用語集全数1、`general-purpose`＋`model:'fable'`＋`effort:'high'`）を並列投入し、各自が公式テキストの担当範囲を通読して指摘だけ返す形で実施した。監督（Fable）が高・中の全件を grep で裏取りしてから [docs/REVIEW_FINDINGS.md](../docs/REVIEW_FINDINGS.md) の R2 セクションに記録。

**結果**: 骨格レベルの乖離ゼロ（R0 との決定的な違い）。検出は**高2・中10・低15**。高2＝s11-01 解説の粒度順が正解と逆／L13 の「2段階フィルタ」の中身がサイト自身の教えと矛盾。中には L9_BODY の div 閉じ漏れ（構造欠陥）、HITL の参照 Sec 誤り、実装と教材の不一致（弱点マップの表示・問題数230）を含む。

**「Fable に価値があるか」の実測結論**: あった。公式原文内の矛盾（フォーム送信の帰属揺れ・ハーネス/コンテキストエンジニアリングの呼称併存）まで検出し、Opus 自身が書いた解説の論理逆転（s11-01）も拾った。ただし用途はレビュー（盲点探し）に限る。修正（G2）以降の実装 Build は Opus 監督に戻す。

修正の追跡は STATUS.md「次にやること」の G2 と REVIEW_FINDINGS.md R2 が持つ。本ファイルの役割（レビューをやるかどうか・どうやるか）は完了したためクローズ。
