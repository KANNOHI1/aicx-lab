テキスト入手前の全 Build（B8〜B11・C1・C2・D1・D2）が終わった後に、全教材・全問題へ**横断の敵対的レビューを1回だけ**入れる。HK 決定（2026-08-28、2026-08-29 に再確認）。

**3段階に分ける**

| 段 | 担当 | 見るもの |
|---|---|---|
| ① 機械検出 | node スクリプト | 長さ手がかり・型3順位語・ID重複・ケース字数・用語リンク漏れ。**モデルには出さない** |
| ② 本体レビュー | **Opus** | 事実誤り・正解の一意性・回跨ぎの矛盾・配分の穴・誤答肢の思想。判断が要るものだけ |
| ③ 見落とし探し | **Fable × effort:max** | ②の結果を渡し、completeness critic として「何が抜けているか」だけを問う |

**Why この配分か**
- 機械で潰せるものをモデルに出すのはトークンの無駄。②に集中させる
- B5 で Opus×28体が実欠陥4件を検出した実績があるので、本体は Opus で足りる見込み
- **「Fable でなければ検出できない」証拠は現時点で無い**。だから Fable は最後の見落とし探しに限定し、使用量を抑えつつ「Fable に価値があるか」を実測する。**③で何も出なければ、以後は Opus で足りると判断してよい**
- C1（模試エンジン）はコードなので別レンズ（動作検証：採点・タイマー・中断保存・localStorage）

**How to apply**
- **③に入る時点で「/model で Fable に切り替えてください」と HK にリマインドする。** Claude 側からモデルは変更できない
- 各 Build の安価な自己チェック（①相当）は最終レビューを待たず毎回やる。最終レビューだけにすると未検証 Build が積み上がる — 実例として第1〜7回に長さ手がかりが35件残り、2026-08-29 に一括是正する羽目になった
