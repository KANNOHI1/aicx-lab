作問Build（B2〜B11・C2・D1・D2）では、実装後・commit 前に **node スクリプトで機械チェック**を通す。モデルに判断させない。

**チェック項目と閾値**

| 項目 | 基準 |
|---|---|
| 正解肢が4択で**単独最長**の割合 | **7割未満**に抑える（同値のタイは数えない） |
| 正解が2位より25%以上長い問題（「強い手がかり」） | **0〜1件**に抑える |
| type:3 の問題文に順位語（「最も優先」「最初に」）があるか | 全件必須（DESIGN §3.2） |
| ID 重複・ケース字数120〜250・limit:180・4択 | 違反0 |
| 新規用語が教材本文に完全一致で出現するか | 全件（linkify は本文のみ対象、`kw` チップは対象外） |

**Why**: 選択肢はシャッフルされるので「いつもAが正解」の手がかりは消えるが、**文字数はシャッフルしても変わらない**。正解肢は条件を全部書くので自然に長くなり、誤答は一言で済むため短くなる。結果「一番長いのを選ぶ」で正答できてしまい、**模試プールが習熟度の計器として機能しなくなる**。HK が「仕上がった」と誤判定するのが最大の害。

**発見の経緯**: 2026-08-28、B5 で初めて敵対的レビュー workflow（Opus×28体）を回したところ、この欠陥を含む4件が検出された。B6 以降は実装中に自己適用している。

**2026-08-29 に第1〜7回を一括是正済み（強い手がかり 35件 → 0件・単独最長率は全11レッスンで70%未満）**。是正時に分かったこと3点:
1. STATUS の記録では「第1〜4回27件」だったが、実測すると**第5回7件・第6回1件・第7回1件も残っていた**（計35件）。B5 の記録は「最長率 91%→68%」であって強い手がかりの件数ではなかった
2. **指標に誤りがあった**。全肢が同じ長さの問題（例 `m03-08` は4肢とも2文字）を「正解が最長」と数えていたため過大計上していた。**タイは手がかりを与えないので「単独最長」で測る**
3. 是正は**誤答肢を伸ばす**方向で行う。正解肢を削ると条件の情報が落ちる（正解を縮めたのは c01-01・c02-02 の2件のみ）

**How to apply**: 実装スクリプト実行後、node の vm で `index.html` の script 部（用語リンク化の手前まで）を eval して QB を取り出し集計する。閾値超過分は**誤答肢を長くする**方向で直す。

**選択肢を書き換えたら解説との整合を必ず検査する。** 解説は「〜が誤りの理由：」で選択肢を要約引用しているため、文言を変えると対応が切れる。**編集前後で同じ検査を回して差分だけを見る**こと（全件検査だと元からの要約引用が141件出てノイズに埋もれる。差分にすれば実際の回帰2件だけが残った）。置換は**選択肢1本ずつ**行う（ファイル内で改行が挟まるため複数肢の連結文字列はマッチしない）。

**2026-08-30 追記：F シリーズの差し替えでも同じ検査を通す。** F1（31問を全問差し替え）では、書きながら「正解肢を単独最長にしない／2位比+25%以内に収める」を守り、`node tools/qcheck.js` で全20項目クリア・単独最長46%（230問全体）だった。**書いてから直すより、書く時点で誤答肢の長さを揃えるほうが早い。**「〜が誤りの理由：」の引用は誤答肢の文言と 75% 以上一致させておくと、項目6の WARN に新規が出ない（F1 では新規ゼロ）。
