**一次資料（公式テキスト・仕様書・書き起こし・大量ログ）を通読してから成果物を書くタイプの作業は、「何個のタスクをこなすか」ではなく「何行の一次資料を読むか」でセッションを割る。**

**Why**: この種の作業では、コンテキスト消費のほぼ全部が①一次資料の通読量と②書き出す成果物の字数で決まる。上限を超えると auto-compact が走り、**一次資料の記憶が要約に置き換わったまま成果物を書き続けることになる**。これは「読まずに推測で書く」のと同じ状態で、しかも自分では気づけない — 要約は自然な文章として残るので、欠けた部分が欠けていることが見えない。aicx-lab では、まさに「シラバスのキーワードから推測して書いた」ことで公式テキストとの乖離が深刻度「高」47件出て全面再構築になった（[[feedback_primary_source_first]]）。圧縮による記憶劣化は、それと同じ失敗を機械的に再現する経路になる。

**How to apply**:

1. 着手前に、そのセッションで通読する一次資料の行数（またはページ数）を数える
2. 実測の目安: **一次資料750行の通読＋成果物 約12,000字（教材1本＋設問22問）でコンテキスト 23%**（Messages 162k / 1M）。会話開始前の固定オーバーヘッドが 63.5k（システムプロンプト・ツール定義・メモリファイル・スキル）ある前提
3. **通読が 1,000行を超えるなら着手前に分割する。** 分割単位は進行表・計画ファイルの側に書き、次セッションが判断し直さなくて済むようにする（分割の根拠を持っているのは今のセッションだけ）
4. 分割したら、各セッションは1単位だけやって終える。「余力があるから次も」をやると、次単位の一次資料を読み込んだ時点で圧縮域に入る
5. 消費を減らす手は通読量を減らすことではない（それは精度を落とす）。**生データをメイン会話に入れない・大きな出力は委譲する**などの一般則で削る

**やらないこと**: 「まだ 23% だから続けられる」という残量ベースの判断。残量ではなく、**次に読む一次資料の量**で決める。50% の時点で1,500行を読み始めれば、その作業の後半は圧縮後の記憶で走ることになる。
