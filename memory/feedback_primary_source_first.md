type: feedback
last_verified: 2026-08-30

**やること**: 一次資料（公式テキスト・原典・仕様書）が手に入った時点で、**まず成果物全体との突き合わせを1回走らせる**。局所的な差分補正から入らない。

**やらないこと**: 目次・キーワード・シラバス・要約といった二次情報から本文の中身を推測して作り込むこと。推測で作る場合は「一次資料が入ったら骨格から作り直す」前提を明示して進める。

**Why**:
2026-08-30、aicx-lab（AICX資格の学習サイト）で発覚した。教材14回・問題230問をシラバスのキーワードだけを頼りに構成していたため、公式テキストが本文で定義している枠組みを大量に取りこぼしていた。Opus 8体の横断レビューで**深刻度「高」47件**、第6章に至っては教材が公式とほぼ別物だった。

取りこぼしの型は一貫している——**キーワードは論点の見出しにすぎず、分類の数・段階の名称・判別の軸は本文にしか書かれていない**。実例:

| | サイト（シラバス起点） | 公式テキスト本文 |
|---|---|---|
| 自動化レベル | 別名の5段階 | Lv.1〜Lv.4 の4段階 |
| 業務分解 | 独自の「5要素」 | IPO の3要素（5要素はSIPOC専用） |
| 組織類型の第3型 | 「CoE型」 | 「ハイブリッド型」（CoEは類型名でなく専門組織） |
| チェンジマネジメント | 独自の4段階 | 否認→抵抗→受容の3段階 |
| トリガー・条件分岐・SECI・抵抗曲線 | 語が一度も出てこない | 「試験で問われる」と明記 |

**この分野で最悪の結果は「間違った枠組みを覚えて試験に落ちる」こと**であり、HK もそこを最大のリスクとして全面再構築を選んだ（学習開始の後ろ倒しより、覚え直しのコストを避ける判断）。

**さらに悪かった設計判断**: 「横断レビューは全Build完了後に1回だけ」と決めていた。公式テキストの書き起こしは 2026-08-29 に完了していたのに、突き合わせを既知の2論点（Sec18・Sec27）だけに絞ったため、全面的な乖離の発見が最後まで遅れた。**一次資料の入手はレビューのトリガーであって、レビューの順番待ちにするものではない。**

**How to apply**:
1. 一次資料が手に入ったら、その日のうちに**全体突き合わせを1回**走らせる（章・節ごとに並列エージェントで可。aicx-lab では Opus 8体・約7分で全体を洗えた）
2. 突き合わせの観点は「**一次資料が『ここが重要』と明示している論点が、成果物に存在するか**」を最優先にする。表記のゆれより、枠組みの欠落の方が致命的
3. エージェントの指摘は鵜呑みにせず、**深刻度の高いものは監督が一次資料の行番号を開いて裏を取る**（今回は主要5件を自分で確認して全て正しかったが、確認しない運用は危険）
4. 指摘は必ず**行番号付きでファイルに保存**する（`docs/REVIEW_FINDINGS.md`）。会話コンテキストに置いたままだと再構築時に再調査になる
5. 突き合わせで拾うのは「一次資料に無い語」だけではない。**一次資料と評価の向きが逆になっている記述**を必ず探す。一次資料が「これは失敗ではない」「これは成果である」と明示している事柄を、こちらが失敗パターンとして教えていないか。語の置換で済む前者と違い、後者は**その語を使っていた文の主張ごと書き直す**必要がある
   - 実例（aicx-lab / 2026-08-30）: 教材は「PoC貧乏＝PoCを繰り返すのは失敗」と教えていたが、公式は「繰り返すこと自体は失敗ではなくAIプロジェクトの正常な進行」と明言。語が無いのではなく評価が真逆で、そのまま覚えると本番で逆の判断を選ぶ。失敗の焦点を「回数」から「判断ゲートの有無」へ移して全文を書き直した
