2026-08-30、横断レビューで深刻度「高」47件（第6章はほぼ別物）が判明し、HK 判断で**学習開始を待って全面再構築**することにした。判断理由は「間違った枠組みを覚えて試験に落ちるリスク」が「学習開始が数日遅れるコスト」を上回るため。

## 再構築の原則

**公式テキスト各 Section の「学習のポイント」を教材の骨格にする。** この節は「試験では〜が問われる」と論点を名指ししており、そこが唯一の正。シラバスのキーワードから中身を推測しない。作った枠組みには公式テキストの行番号を根拠として DESIGN.md に残す。

## Build 分割（BUILD_PLAN.md の F シリーズ）

F0（DESIGN改訂）→ F1〜F6（章ごとに教材＋問題）→ F7（用語集）→ F8（総復習ページ・1枚図・型名統一）→ F9（模試再組成）→ F10（最終検証）

章ごとの問題数: Ch1=31 / Ch2=22 / Ch3=66 / Ch4=22 / Ch5=44 / Ch6=45。**Ch3 が最大、Ch6 はほぼ新規**。

## 各 F の完了条件

1. 該当 Section の公式「学習のポイント」の論点がすべて教材に存在する
2. 公式の理解度チェックに相当する設問が問題側にある
3. `node tools/qcheck.js` が全項目クリア（22項目）
4. 公式テキストの行番号を根拠として DESIGN.md に残す

## 作り直さなくてよい資産（重要）

- **Sec 18（3層フレームワーク）と Sec 27（5つの問い）**: Build E で公式へ突き合わせ済み。維持する
- **模試エンジン一式（C1のコード）**: 採点・SRS・中断保存/再開・時間切れ自動提出・章別/型別集計・エクスポート/インポートを実機検証済みで欠陥なし。**問題データが変わるだけで、エンジンは触らない**
- **`tools/qcheck.js`（機械検出22項目）と `tools/mockplan.js`（模試の一括割付）**: そのまま使える
- **サイトの UI・localStorage・SRS の設計**: レビュー対象外だが問題は出ていない

## 各 F の実行手順（F1 で確立した型・2026-08-30）

1. **公式テキストの該当 Section を監督が全文通読する。** DESIGN §4 の行番号だけを拾い読みしない（Sec1-8 は約1,600行。Bash の出力上限に当たるので 200 行ずつ読む）
2. 教材（`LNN_BODY`）を書き直す。公式の枠組み・段階の数と名称・判別鍵をそのまま使い、説明文と例は自作する
3. **問題は ID・sec・ch・type・pool を維持したまま中身だけ差し替える。** これを守れば `MOCKSETS` の125問の割付が壊れず、F9 まで模試が動き続ける。ID を変えると公開済み問題 ID の変更にもあたる
4. その章で廃止した語が用語集（`GLO`）に残っていると qcheck 項目9（用語集にあるが教材本文に無い語）で落ちる。**その章ぶんだけ先に削除・統合する**（用語集の全体再構築は F7）
5. **その回で廃止した枠組みが、他の回の本文や他 Section の問題から参照されていないか `grep -c` で確認して0にする。** 教材は回をまたいで相互参照している（F3a では「第4回の5条件」が第5・7・10・11回の本文と Sec14/15/22/30 の問題に残っていた）。qcheck の項目9は用語集しか見ないのでこれを検出できない。参照だけ残ると学習者は存在しないフレームを探すことになる
6. `node tools/qcheck.js` → 全項目 OK を確認。WARN 2種は裁定済みなので**前回出力との差分だけ**見る
7. Playwright で `openLesson(n)` を呼び、新語の有無・旧語の不在・採点と解説表示・コンソールエラー0件を確認 → commit → push → 本番 URL で確認（GitHub Pages は反映まで30秒ほどかかる）→ 検証サーバーを taskkill し netstat で待受ゼロを確認

**編集の実務**: 大きなテンプレート文字列は heredoc ではなく Write でスクラッチパッドへ書き、node スクリプトでマーカー間を差し替える。`node -e` にバッククォートを含む文字列を渡すとシェルがコマンド置換するので使わない。

## 1つの F に詰め込む量（F2 で実測・2026-08-30）

**判定鍵: そのセッションで通読する公式テキストが 1,000行を超えるなら分割する。**

F2（Sec9-11・約750行の通読＋教材1回＋問題22問）でコンテキストは **Messages 162k / 全体 226k（1M の 23%）**。会話開始前から乗る固定オーバーヘッドが 63.5k（システムプロンプト・ツール・メモリファイル・スキル）ある。消費は**公式テキストの通読量**と**書き出す教材・問題の字数**にほぼ比例する。

分割しないと何が起きるか: F3 を1本で回すと教材3回分＋66問＋公式約2,000行で 60〜70% に達し、後半で auto-compact が走る。**圧縮で公式テキストの記憶が欠けたまま作問すると、F0 で潰したはずの「推測で書く」失敗がそのまま再発する**（＝深刻度「高」47件の原因と同じ構造）。これを根拠に F3 を F3a/F3b/F3c に3分割した。F3a（Sec12-13,16・約800行の通読＋教材1回＋問題22問＋他回の参照掃除）の実測もほぼ F2 と同水準で、分割の判定鍵はそのまま使える。F5（Ch5・44問）・F6（Ch6・45問・ほぼ新規）も2分割を見込む。

## シラバスと公式テキストが食い違う場合の扱い（F2 で確立）

サイト内の `SYL`（シラバス32セクション）は**シラバス Ver1.2 の逐語記録**として扱い、本文と食い違っても書き換えない。こちらが片方に寄せると出典が失われる。**教材・解説の側で「シラバスはこう言うが、本文の定義はこれ」と書き分け、DESIGN §7 の未確定事項へ記録する。**

実例（Sec9）: シラバスの到達目標は「業務を**目的・入力・処理・出力・関係者**の観点で分解」だが、公式テキスト本文が定義する IPO は**入力・処理・出力の3要素**（L1941-1949）で、5要素は SIPOC 専用（L2572）。**IPO は3要素を正**とし、シラバスの5観点は「分解の観点であって IPO の構成ではない」と解説に書いた。
